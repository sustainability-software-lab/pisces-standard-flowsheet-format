Development Notes — August 2026

August 1 – 18, 2026 v0.0.5 → v0.1.3 by Sarang S. Bhagwat

The past few weeks were busy ones for the Standard Flowsheet Format, its validator, and the BioSTEAM exporter — eleven releases in all. The short version: SFF has grown from a promising export format into something we are now comfortable calling a standard, with a published requirements catalogue, a two-layer validator, provenance tags a machine has actually checked, and files that can prove they are reproducible. All of it was built with the whole PISCES ecosystem in mind — the flowsheet database, the LLM extraction pipeline, and the exporters now taking shape for other simulators (SuperPro, Aspen Plus).

  • Tags: provenance a machine has checked. A declared tag that fails verification is a validation error, so tags can be trusted, not just read.

Validation: two layers, graded findings

Validation is now two layers in one module, fully decoupled from any simulator:

  • validate_json_against_schema() — the structural JSON-Schema gate: types, required fields, enums, and the declarative constraints added in 0.0.12.
  • validate_flowsheet_against_SFF() — runs the schema gate plus every semantic check in the catalogue — all 48 of them, surveyed below.

The catalogue behind that second layer, sff_checks.md, deserves a closer look. Each of its 48 requirements is a full record, not just a rule: a statement, a rationale (what breaks for a downstream consumer without it), a severity, an explicit “skipped when” condition, and its enforcement home (schema, validator, or both). The checks are organized into families keyed to the document's sections:

MET 7UNIT 10STR 14CHEM 5UTIL 5QU
48 checks by family — rightmost segments: QU 4 · XREF/GRAPH/TAG 3.
MET7Metadata — sff_version is valid semver, feedstock and product references resolve to real streams, TEA_year is plausible, and embedded reproducibility content actually matches its SHA-256 digests.
UNIT10Units — unique IDs, no orphan units, utility results keyed to declared utilities, reactions with valid conversions and well-formed stoichiometry, and complete purchase-cost correlations.
STR14Streams — the largest family: unique IDs, endpoints that resolve to a unit or the boundary, exactly one topology role that agrees with the actual connectivity, composition fractions that sum to one, phase flows that sum to the stream total, and mass flow that agrees with molar flow × molar mass.
CHEM5Chemicals — unique IDs and indices, positive molar mass (a warning since 0.1.1), and formula-derived molar mass agreeing with the declared value.
UTIL5Utilities — unique IDs across all utility groups, valid compositions, physically sensible temperatures and pressures, and no utilities declared but never used.
QU4Quantity units — every quantity field resolves to a registered unit, unit strings actually parse, and aliases are globally unambiguous.
XREF2Cross-object & graph (with GRAPH) — an aggregate referential-integrity gate over all the ID cross-references, and the requirement that the flowsheet has at least one boundary inlet and one boundary outlet — a process that consumes nothing and produces nothing is, at minimum, suspicious.
TAG1Tags — declared tags are verified, as described in the next section.

Numeric checks compare against named default tolerances (fraction sums within 10−6 absolute; flow agreement within 10−3 relative), and the material-balance scope is deliberately modest: local, per-stream self-consistency only — no system-wide closure, no elemental balances. We would rather catalogue checks an honest file can pass today than aspirations it cannot.

Every finding is a CheckResult carrying its check ID, a severity (error | warning | info), an outcome (pass | fail | skip), a message, and a JSON path. Only error-severity failures make a file non-conforming — warnings and infos are guidance, not gates. The engine is deliberately robust: a schema-invalid document still runs the structural checks, a crashing check is contained as a finding rather than sinking the run, and a skip always means "inputs absent," never a silent pass.

Tags: provenance a machine has checked

Tags answer the question: what level of detail does this flowsheet include? Four tags exist in two classes. The three static tags are verified by passing a tag-specific subset of the catalogue's checks with no warning-severity findings — fast, no simulation needed. The harness tag, reproducible, is verified the hard way: by actually re-running the file's embedded recipe in its pinned environment and deep-comparing the result.

Re-run the embedded recipe in its pinned environment → deep-compare within comparison_rtol.
Either lane resolves every declared tag to one of:
earned — the tag is trustworthy: it was verified against the file itself.
declared but unearned — a validation error (TAG-01).

Two public entry points support this: evaluate_sff_tags() returns a per-tag verdict — its earned / declared / blocking fields — with the specific check IDs blocking each tag that fails verification, and verify_reproducible() runs the heavy harness path. The BioSTEAM exporter stamps exported-from-simulator only when the tag verifies against the document it just assembled — and never stamps reproducible itself; that always requires the harness. The corpus's reference file, SF_BST_01.json (corn dry-grind ethanol), now carries both tags, verified end to end.

Reproducible exports, end to end

A key new feature is the model recipe: a self-contained, three-file description of how a flowsheet export is produced. load.py holds the code that builds the model, plus its export flags; environment.yaml pins the exact conda environment; and extended_metadata.yaml records what only a human knows — source DOI, process title, flowsheet designers, microbial hosts. The division of labor is deliberate: code and its environment on one side, human-authored provenance on the other.

A new harness completes the loop. It provisions the pinned environment, runs the export inside it, and embeds the full recipe verbatim — with SHA-256 digests — into the exported file itself, so a flowsheet carries its own instructions for rebuilding it. regenerate_corpus() (also available as a python -m command) drives the whole pipeline, with an opt-in pass that verifies and stamps the reproducible tag. Line endings are pinned to LF repo-wide because the digests are computed over verbatim bytes — reproducibility is taken literally here.

  • Continuous integration — the full suite, including both simulating tiers, runs on Ubuntu and Windows on every push and pull request.
  • Deterministic output — utility agents sorted by ID, reactions in stable discovery order, synthesized IDs for unnamed streams: re-exports diff cleanly.

A model↔flowsheet registry

The corpus and its model recipes now follow a permanent naming convention: model recipes are M_<SIM>_<NN> and exported flowsheets SF_<SIM>_<NN> (BST = BioSTEAM), where the numbers are opaque, permanent IDs — so SF_BST_01 is a stable name you can safely cite, link to, and key a database on. The model-to-flowsheet pairing lives in one registry file, all_models.yaml, the single source of truth: it drives corpus regeneration (a recipe on disk must be registered before it can export, and regenerate_corpus now offers the opt-in --stamp-reproducible pass from the command line), and it generates the human-readable model and flowsheet index READMEs, which a pre-commit hook and a sync test keep from ever drifting out of date. The old descriptive filenames remain fully traceable through git history (git log --follow).

Documentation, rebuilt — and now on Read the Docs

The documentation site has been rebuilt from the ground up and now lives on Read the Docs at pisces-standard-flowsheet-format.readthedocs.io: a Getting Started guide, a concept page on the graph model, a full Schema Reference generated from the schema itself, a Validation & Checks section citing the catalogue IDs, an auto-generated API reference, and four runnable tutorial notebooks — validating an SFF file, reading and traversing a flowsheet, working with tags and reproducibility, and a full BioSTEAM export walkthrough.

The site also includes an interactive schema visualization: the whole SFF schema as an explorable graph that starts collapsed, expands one level per click, and shows each field's description on hover — the fastest way to build a mental model of the format before reading a line of the reference.

What this means for you

If you use flowsheets from the PISCES database

Reach for:metadata.tagstutorialsSF_BST_01

Once these SFF updates propagate to the PISCES website — look for the tags. A file tagged exported-from-simulator came straight from a process simulator and passed the export-quality checks; one tagged reproducible can be regenerated from the recipe embedded inside it. And because an unverified tag is a validation error, a tag you see is a tag a machine has verified. The new tutorials will get you from download to a traversed flowsheet graph in a few minutes.

If you build the PISCES website

Reach for:metadata.tagsstream rolesTEA_currencyquantity_units_globalregistry IDsCheckResult

Several new fields are designed to be surfaced directly: metadata.tags as trust badges, stream roles for laying out and annotating flowsheet diagrams (feedstocks in, products out — no graph inference needed), TEA_currency for unambiguous cost display, and the unit registries (quantity_units_global plus per-unit design-result units) for rendering any quantity with its correct unit from one lookup. Corpus flowsheets also now carry permanent registry IDs (SF_BST_01, SF_BST_02, …) that are safe to use as database keys and URL slugs — they will never be renamed.

For validation UI, the new comprehensive validator — validate_flowsheet_against_SFF() — turns any SFF file into a structured quality report: each CheckResult it returns gives a findings panel everything it needs — stable ID, severity, outcome, message, and JSON path — and the catalogue IDs are stable enough to deep-link to their documentation.

If you build the LLM extraction pipeline

Reach for:extracted-from-proseextracted-from-imagevalidate_flowsheet_against_SFF()evaluate_sff_tags()severity ladder

Two of the four tags — extracted-from-prose and extracted-from-image — exist for extracted flowsheets. The substantive floor behind them (UNIT-10, STR-14: units and streams present and well-identified) is the quality bar an extraction must clear. The new comprehensive validator, validate_flowsheet_against_SFF(), makes a natural scoring function for candidate extractions — it runs all 48 catalogued checks and grades every finding — and evaluate_sff_tags() reports exactly which checks block a tag from verifying, a ready-made feedback signal for the pipeline.

The v0.1.1 molar-mass relaxation was made with extraction in mind: a chemical whose molar mass couldn't be recovered from the source no longer fails schema validation — it draws a warning instead. The severity ladder maps cleanly onto a pipeline gate: reject on errors, iterate on warnings.

If you're writing an exporter (SuperPro, Aspen Plus, …)

Reach for:sff_checks.mdvalidate_flowsheet_against_SFF()versioned-exporter patternthree-file recipe

The path is now well paved — you should have an easier time of it than we did. sff_checks.md is the authoritative statement of what a conforming file must satisfy — write against it, not against the BioSTEAM exporter's behavior. The validator is simulator-agnostic, so validate_flowsheet_against_SFF() is your acceptance test from day one.

Patterns worth borrowing from the reference implementation: one thin exporter function per schema version (so your historical exports stay stable as the format evolves), conditional tag stamping (declare exported-from-simulator only when it verifies against the assembled document), and the three-file recipe layout if you want your exports to verify as reproducible. The purchase-cost-correlation block (0.1.2) is optional — emit it if your simulator exposes parametric costing, omit it cleanly if not.

Looking ahead

The near-term roadmap: refreshing the remaining corpus files to the current shape with full reproducibility recipes, growing the model-recipe library, and SFF → NetworkX graph conversion — loading any SFF file directly as a NetworkX directed graph, so the traversal, path-finding, and network-analysis tooling of that ecosystem works on flowsheets out of the box. A model-aware energy-balance check is a welcome future addition (a naive per-unit enthalpy balance proved too noisy to be useful, so we're holding out for a design that won't cry wolf). If you're building on SFF and a check, field, or tag would make your life easier, the catalogue-first process is exactly how it gets in: propose the requirement, it gets an ID, and then it gets implemented.

Version log

0.0.6

Reproducibility metadata & model recipes

An optional metadata.reproducibility block embeds the pinned conda environment, the model-loading code, and authored extended metadata verbatim, each paired with a SHA-256 digest (MET-07 verifies content against digest). This is the foundation everything in the tag layer builds on.

Arriving alongside it: the model recipe — load.py plus a pinned environment.yaml, later joined by extended_metadata.yaml (0.0.10) — and the harness that provisions the pinned environment and runs the export inside it. The reproducibility block is, in effect, the recipe riding along inside the file.

0.0.7
shape change

Quantity-unit registries

Physical quantities became bare numbers, with units declared once in a top-level quantity_units_global registry and a per-unit quantity_units_for_design_results map — replacing the older inline {value, units} pairs. Files are leaner, and consumers resolve units from one place instead of thousands.

0.0.8
shape change

Required TEA currency

metadata.TEA_currency is now required. A cost without a currency is a number, not a result — files now say which one they mean.

0.0.9
shape change

Per-phase streams

Stream properties gained a phases structure, capturing composition and conditions per phase — essential for flash drums, distillation, and any multiphase separation.

0.0.10

Stream roles & authored metadata

An optional roles array declares what each stream is: exactly one topology role (input | output | internal) plus optional designations (feedstock, product, purchased_raw_material). Renderers and analyses no longer need to re-derive this from the graph.

Alongside it, model recipes gained a human-authored extended_metadata.yaml carrying source_doi, process_title, flowsheet_designers, and microorganisms — the things a human knows about a flowsheet that no simulator can tell you.

0.0.11

Enthalpy flow

Streams may carry an optional enthalpy_flow property, rounding out the mass/energy picture available per stream.

0.0.12

The requirements catalogue, encoded

sff_checks.md landed as the authoritative catalogue, and the schema was tightened to enforce its declarative constraints directly: semver-patterned sff_version, 64-hex reproducibility digests, reaction conversions bounded to [0, 1], positive stream pressures, required total_mass_flow, and more. The exporter also began synthesizing unique IDs for unnamed auxiliary streams so no two streams can collide.

0.1.0

Milestone release

No shape change — a deliberate marker that the format, its catalogue, and its validator had reached a coherent baseline worth naming.

0.1.1

A friendlier molar-mass rule

The schema's hard requirement that molar_mass be positive (CHEM-02) moved into the validator as a warning. A file with a placeholder or unknown molar mass is now structurally valid but flagged for improvement — a deliberate widening for producers, like extraction pipelines, that can't always recover every property.

0.1.2

Purchase-cost correlations

Each unit gains an optional purchase_cost_correlations object recording the parametric correlation behind each cost item — basis, reference size and cost, scaling exponent, and cost-year index (CEPCI). Consumers can re-derive equipment cost at a different design size or cost year instead of treating costs as opaque numbers. Checked by UNIT-08/UNIT-09.

0.1.3

Provenance & quality tags

An optional metadata.tags array declares machine-verified provenance claims — see the tags section above. A declared tag that fails verification is a validation error (TAG-01), so tags can be trusted, not just read.
